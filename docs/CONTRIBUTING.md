# go-netx 开发与测试规则

本文档是所有协作者必须遵守的规则，人和 AI 都一样。规则背后的设计依据见 [ARCHITECTURE.md](../ARCHITECTURE.md)，测试矩阵见 [TESTING.md](TESTING.md)。

规则用“必须”“禁止”“应当”表述：违反“必须”和“禁止”的改动不会被合并；“应当”表示没有特殊理由时都要遵守。

## 1. 推送前检查

**每次推送前必须运行 `make verify`，并且全部通过。** 它依次执行：

| 步骤 | 命令 | 检查内容 |
|---|---|---|
| 格式 | `make fmtcheck` | 所有文件都已经过 `gofmt` |
| 静态检查 | `make vet` | `go vet ./...` |
| 文档一致性 | `make doccheck` | TESTING.md 与测试代码一一对应（第 3 节） |
| Race | `make race` | `go test -race`，普通构建和 `netxdebug` 构建各跑一轮 |
| 交叉编译 | `make cross` | 对 linux/amd64、linux/386、darwin/arm64、windows/amd64、freebsd/amd64、js/wasm 执行 `go vet` |

- 禁止推送没有通过 `make verify` 的提交，包括“只改了测试”的提交。
- 只在某个平台上运行的测试（比如只在 macOS 运行），如果本地没有那个平台，至少要保证 `make cross` 能编译通过，并在 PR 描述中写明“未在该平台上实际运行”。
- 新增或修改了并发相关的测试，应当再单独连续运行 20 次，确认不会偶发失败：

  ```sh
  go test -race -count=20 -run '<测试名>' ./<包>
  ```

## 2. 测试的写法

### 2.1 每个测试都必须声明它检查什么

每个 `Test`、`Benchmark`、`Fuzz` 函数都必须在注释的最后一行写上 `Checks:` 声明，列出它覆盖的检查点 ID：

```go
// Checks: UDP-21, UDP-22
func TestReplyValidatesPacket(t *testing.T) {
```

- ID 必须是 TESTING.md 中已经存在的检查点。
- 没有合适的检查点时，先在 TESTING.md 对应模块下新增一个，再写测试。
- 一个测试可以覆盖多个检查点，一个检查点也可以由多个测试覆盖。
- 只声明这个测试真正断言了的检查点，不能把“顺带执行到”的代码也算进去。

### 2.2 测试必须稳定

- 禁止用 `time.Sleep` 等待异步结果后直接断言。要轮询条件并设置超时，或者等待 channel。
  （反例：先发包、sleep，再检查计数。正确做法：轮询 `Stats()`，直到计数满足条件或超时。）
- 断言异步计数时要考虑先后顺序。例如客户端可能在服务端累加计数之前就收到了回包。
- 每个测试都必须自行清理：关闭监听、停止服务、等待 goroutine 退出。可以用 `t.Cleanup`。
- 监听地址一律使用 `127.0.0.1:0` 这类随机端口，禁止写死端口号。

### 2.3 平台相关的测试

- 只能在特定平台运行的测试，必须放在带构建标签的独立文件里，比如 `xxx_linux_test.go`、`xxx_darwin_test.go`，或者在文件开头写 `//go:build unix`。
- **禁止通过给已有测试文件加构建标签来缩小测试范围。** 如果一个文件需要限定平台，必须把其中原本跨平台的测试移到一个不带标签的文件里，确保每个平台的测试数量不会减少。
  （反例：给 `socket/options_test.go` 加上 `//go:build unix` 后，Windows 上 socket 包一个测试都没有了。）
- 平台差异要写进测试，而不是跳过：同一个检查点在不同平台上的预期不同时，分别断言各自平台的行为。

### 2.4 禁止的做法

- 禁止删除测试，或者减弱测试中的断言来让测试通过。测试失败说明代码有问题，或者测试本身有问题；如果确实是测试写错了，要在提交说明中解释原因。
- 禁止用 `t.Skip` 掩盖失败。只有在当前平台根本不具备被测能力时才能跳过，并且要写明原因。
- 仅包含测试的分支，禁止修改非测试代码。发现 bug 时，另开分支修复，或者先在 TESTING.md 登记为 🔧。

## 3. 文档与测试的对应关系

TESTING.md 的“测试”一栏由工具根据代码中的 `Checks:` 声明自动生成，**禁止手工编辑**。

### 3.1 新增或修改测试的流程

1. 写测试，在函数注释里加上 `// Checks: <ID>`。
2. 把 TESTING.md 中对应检查点的状态改为 ✅ 或 ⚠️；⚠️ 时，在“说明”一栏写清楚还缺什么。
3. 运行 `make testdoc`，重新生成“测试”一栏。
4. 运行 `make verify`。

### 3.2 状态的含义

| 标记 | 含义 | 能否被测试声明 |
|---|---|---|
| ✅ | 已覆盖 | 必须至少有一个测试 |
| ⚠️ | 部分覆盖，“说明”一栏写明缺什么 | 必须至少有一个测试 |
| ❌ | 尚未覆盖 | 禁止 |
| 🔧 | 已知代码问题，尚未修复 | 禁止（修复后改为 ✅ 并补测试） |
| ➖ | API 有意不提供该行为 | 禁止 |
| ⚙️ | 由命令保证，例如 race、交叉编译 | 禁止 |
| ❓ | 设计待定 | 可以 |

### 3.3 工具会拦截的情况

`go test ./...`（检查点 DOC-01）和 `make doccheck` 在以下情况都会失败，并指出具体的文件和行号：

- 测试函数没有 `Checks:` 声明；
- 声明了 TESTING.md 中不存在的 ID；
- ✅ 或 ⚠️ 的检查点没有任何测试；
- ❌、🔧、➖、⚙️ 的检查点却已经有测试声明它；
- 回归清单引用了不存在的检查点；
- “测试”一栏没有重新生成。

## 4. 问题的登记与关闭

- Review 中发现的问题，必须在 TESTING.md 第 12 节登记一个新的 REG 编号，并对应到一个检查点；该检查点标为 🔧。
- 修复时，必须在同一个 PR 里补上能复现该问题的测试，把检查点改为 ✅，REG 的状态也改为 ✅。**REG 这一行永远不删除。**
- 讨论后决定不修改的，登记到“设计决定”（D-xx），写明理由，以后不再重复讨论。
- ID 不复用：检查点删除后，它的 ID 也不再分配给其他检查点。

## 5. 代码改动

- 包结构、依赖方向、所有权规则以 ARCHITECTURE.md 为准，那里列出的冻结规则同样适用。
- 新增公开 API 时，同一个 PR 里必须在 TESTING.md 中为它新增检查点，并更新 CHANGELOG.md。
- 删除或修改公开 API 属于破坏兼容性的改动，必须提升主版本号，并在 CHANGELOG.md 中写明迁移方法。
- 热路径上的改动（UDP 读写、buf、queue、flow 查找）必须在改动前后各运行一次 `make bench`，并把分配次数的对比写进 PR 描述。热路径的分配次数禁止增加。

## 6. 分支、提交与 PR

- 分支应当基于最新的 `main`，或者基于它要合入的那个 PR 分支。推送前先拉取目标分支的最新代码。
- 一个分支只做一件事：修 bug、补测试、加功能分开进行。
- 提交说明的第一行写清楚改了什么，正文写为什么改；补测试的提交写明覆盖了哪些检查点 ID。
- PR 描述必须包含：改动内容、涉及的检查点和 REG 编号，以及 `make verify` 的结果。实际没有运行过的测试（例如其他平台），必须明确写出“未运行”。
- 合并后打版本标签：在 GitHub Releases 中以 `main` 为目标发布，说明直接复制 CHANGELOG.md 中对应版本的内容。

## 7. 规则的修改

本文档和 TESTING.md 第 0.1 节一起构成测试规则。修改规则时，要在同一个 PR 里同步更新这两处，以及 Makefile 中的 `verify` 目标。
